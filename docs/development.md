# Development

ESP-IDF 6, built with PlatformIO. The display design is generated by Python from an empty Nextion project and
compiled with the Nextion Editor under wine.

## Building

    pio run -e nspanel                 # the firmware for the NSPanel EU (the icon set embedded)
    pio run -e nspanel -t upload       # flash it over the serial port
    test/host/run.sh                   # the host tests (the display logic, the formats, the schema, openHAB, the Nextion protocol)
    node tools/check_ui.js             # the web interface starts on every entry point
    boards/nspanel/nextion/build.sh eu # the display design (needs the Nextion Editor under wine, ~25 min)

A build writes, in `.pio/build/nspanel/`:

| File | For |
|---|---|
| `ohpanel-nspanel-eu-firmware-<version>.bin` | an update over WiFi (Settings > Firmware) |
| `ohpanel-nspanel-eu-factory-<version>.bin` | the first flash, at offset 0 (bootloader, partition table, firmware) |

and `boards/nspanel/nextion/build.sh` writes `build/ohpanel-nspanel-eu-display-<version>.tft`, the display
design; its version is the one the firmware expects (`display-manifest-eu.json`), and the web interface asks for
the file by that name when the display runs another one. The version is a hash of the design's content: a change
to the recipe that leaves the design as it was keeps it, and panels need no new display firmware for it.

### Panel variants

Each panel variant has a firmware and a display design of its own (`tools/variant.py`): `eu`, the NSPanel EU
(landscape, its frame hiding the rightmost 30 px; environment `nspanel`), `us`, the NSPanel US (portrait,
320x480; environment `nspanel-us`), and `us-landscape`, the NSPanel US on its side, its buttons on the right
(480x320, all of it visible; on home the relays' labels upright beside the buttons, in a turned font; environment
`nspanel-us-landscape`). The variant is `custom_variant` of the environment
in `platformio.ini`; it picks the display manifest (`boards/nspanel/nextion/display-manifest-<variant>.json`) and
the preview's layout (`www/layout-<variant>.json`), names the release files (`ohpanel-nspanel-<variant>-...`) and
the firmware's project (`CMakeLists.txt`: `ohpanel` for the EU, `ohpanel-us`, `ohpanel-us-landscape` for the US),
so a panel refuses an update meant for another variant -- the US's two take each other's (the same panel turned). `boards/nspanel/nextion/build.sh <variant>` builds the variant's design:
`boards/nspanel/nextion/layout.py` takes `OHPANEL_VARIANT` and is `layout_eu.py` or `layout_us.py` (the same names,
the same objects on every page, as many a sheet: the firmware fills both alike), and the pictures that depend on
the layout (backgrounds at the display's size, tiles, controls, the logo) are the variant's
(`boards/nspanel/nextion/assets/<variant>/`, written by `assets/generate.py`); CI and the release build every
variant that has one (`pio run $(python3 tools/variant.py)`).

## The panel's languages

The words the panel writes, in every display language, are in `components/app_display/texts.json` (with each
language's number separators and default date format). `tools/gen_texts.py` writes them into the firmware
(`Format.cpp`: tables of C strings in flash), the web interface's preview (`www/index.html`) and the schema's list
of languages; edit the JSON, then run it. `tools/gen_texts.py --check` (in `ci.yml`) fails when they differ.

## Layout

    components/        the firmware's parts, the same on every board: settings, network,
                       openHAB, storage, web interface, panel configuration, display logic
    src/               the application (main loop, buttons, recovery, diagnostics)
    boards/<board>/    what one device needs: its hardware as a component (board/: pins,
                       relays, buttons, sensors), its partition table, its display design
                       (nspanel/nextion/), chosen by OHPANEL_BOARD in CMakeLists.txt
    www/               the web interface (one file, embedded into the firmware)
    demo/              the web interface's demo: a mock of the panel's API and invented data
    logo/              the logo, written by make.py
    tools/, test/      build helpers, the host tests

One board so far: the Sonoff NSPanel EU (`boards/nspanel`).

## The demo and the screenshots

The web interface runs without a panel: `demo/mock.js` answers every `/api/v1/...` call in the browser from
`demo/config.json` (the panel's configuration), `demo/items.json` (an invented openHAB) and `demo/api.json`
(what the status pages show). The display preview draws from them as from a panel.

    tools/build_demo.py             # build/demo: a static site, served by any web server
    tools/screenshots.mjs           # docs/images/screens: every page of the demo's panel and the web interface
    tools/make_hero.py              # docs/images/hero.png: the README's title picture

`screenshots.mjs` needs Chromium and Node 22, nothing else. After a change to the display design or the web
interface, run the three again: the pictures follow.

The GitHub workflow `pages.yml` publishes the landing page and the browser flasher (`site/`, `site/flash/`) and the demo on GitHub Pages,
and with `tools/pages_updates.py` the files of the latest release and of the latest test build when it is newer
(`update/stable/`, `update/test/`: per panel the factory image, the firmware and the display design, and
`update.json` with their versions and SHA-256): what the flasher installs and the web interface's update fetches,
since a release's own files cannot be fetched from another page.

## Releases

A release has the sources (GitHub adds them) and a zip per panel variant, `ohpanel-nspanel-eu-<version>.zip`,
`ohpanel-nspanel-us-<version>.zip` and `ohpanel-nspanel-us-landscape-<version>.zip`, each with that panel's binaries and the licences that must go with every copy of
them (the fonts' licences ask for that). The workflow
`release.yml` makes it from a tag:

    boards/nspanel/nextion/build.sh eu    # only after a change to the display design: the Nextion Editor under wine
    git add boards/nspanel/nextion/display boards/nspanel/nextion/display-manifest-*.json www/layout-*.json
    $EDITOR docs/releases/1.0.0.md        # the release notes (without them GitHub writes some)
    git commit ... && git tag v1.0.0 && git push && git push --tags

The display design is the one file GitHub cannot build, so `build.sh` keeps a copy in
`boards/nspanel/nextion/display/` (the old one removed), committed with the manifest that names it. On the tag the
workflow builds the firmware, runs the host tests, makes the zips with `tools/make_release.py`, publishes the release
and starts `pages.yml` again, a test build too: the flasher and the web interface's update take the new files. `make_release.py` also works locally; it
refuses a firmware built from uncommitted changes (`-dirty`) and a missing display design.

The workflow `ci.yml` runs the firmware build, the host tests, the web interface check and the demo on every push.
