A test build for [#1](https://github.com/bruestel/ohpanel/issues/1): the display design could not be written to a
display that runs Sonoff's own design (a panel from the shop, or one that ran Tasmota).

**Fixed**
- Before writing the display design, OHpanel now switches the display off and on. The firmware that ran before
  (Sonoff's, or Tasmota's NSPanel driver) puts the display in protocol reparse mode, where it executes no command and
  answers only with buffer overflows (status 0x24); a restart of the ESP alone does not end that mode.
- A display in that mode is asked to leave it, when looking for the display and before writing the display design.
- Writing the display design took any byte from the display as the confirmation of a block, the 0x24 overflows too:
  the upload "succeeded" while nothing was written. Only the confirmation itself (0x05) counts now; anything else
  ends in an error that says what the display answered.

**Install**
- Already running OHpanel: Settings > Firmware with `ohpanel-nspanel-eu-firmware-0.9.1-rc2.bin` from
  `ohpanel-0.9.1-rc2.zip`, then write the display design (`ohpanel-nspanel-eu-display-bc629e1e.tft`, unchanged).
- Coming from Tasmota or Sonoff's firmware: flash `ohpanel-nspanel-eu-factory-0.9.1-rc2.bin` over the serial port,
  flash erased first ([docs/install.md](https://github.com/bruestel/ohpanel/blob/main/docs/install.md)). An update
  from Tasmota over WiFi keeps Tasmota's partition table, in which OHpanel cannot store its configuration.
